# 데이터베이스 마이그레이션

애플리케이션이 빈 MariaDB 데이터베이스에 연결되면 Flyway가 SQL 파일을
버전 순서대로 적용합니다.

- `V1`: 회원 및 반려동물
- `V2`: 장소
- `V3`: 예약 및 결제
- `V4`: 리뷰
- `V5`: 사용자 비밀번호
- `V6`: 장소 유형 enum 적용
- `V7`: 반려동물 크기 enum 및 출생 연도 YEAR 적용
- `V8`: 장소에 호스트 닉네임 스냅샷 추가
- `V9`: 장소에 리뷰 평균 별점 추가
- `V10`: 예약에 예약번호 추가
- `V11`: 장소 예약 가능 시간을 3시간 슬롯 재고로 재정의
- `V13`: 회원 이메일에 UNIQUE 제약 추가 (기존 중복 정리 포함)
- `V14`: 장소 주소의 지역구 검색 인덱스 추가 (기존 장소 0건으로 백필 대상 없음)
- `V15`: 슬롯 점유 예약(#221)의 `reservation_slots` 추가
- `V16`: 카카오 로그인(#215)의 `users.provider`·`provider_id` 추가 및 `email` NULL 허용

`V12` 는 결번입니다. 슬롯 점유 예약이 `feat/slot-based-reservation` 브랜치에서 `V12` 로
개발되는 동안 `V13`·`V14` 가 먼저 develop 을 거쳐 운영 DB 에 적용됐고, 그 뒤에 `V12` 가
합쳐지면서 운영 DB 의 이력이 `… V11, V13` 이 됐습니다. Flyway 는 이미 적용된 것보다
낮은 번호가 뒤늦게 나타나면 기동을 거부하므로(`Detected resolved migration not applied
to database: 12`), 파일을 `V15` 로 옮기고 `V12` 는 영구히 비워 둡니다. 되살려 쓰면
같은 사고가 반복됩니다. 다음 새 마이그레이션은 `V17` 부터 씁니다.

**브랜치를 오래 들고 있을수록 이 충돌이 납니다.** 마이그레이션 번호는 파일을 만드는
시점이 아니라 develop 에 합쳐지는 시점 기준으로 정해야 안전합니다.

공유 데이터베이스에 이미 적용된 마이그레이션 파일은 수정하지 않습니다.
스키마를 변경할 때는 다음 버전의 마이그레이션 파일을 새로 추가합니다.

`docs/db/schema.sql`은 현재 최종 구조를 확인하기 위한 통합 스냅샷입니다.
일반적인 로컬 실행과 배포에서는 이 파일을 직접 실행하지 않고 Flyway를 사용합니다.

기존 운영 데이터베이스에 처음 Flyway를 적용할 때만 현재 적용 상태를 확인한 뒤
`FLYWAY_BASELINE_ON_MIGRATE=true`와 적절한 기준 버전을 설정합니다. 시작 후
`flyway_schema_history`에 기준 이력이 등록됐는지 확인하고 설정을 다시
비활성화합니다.
